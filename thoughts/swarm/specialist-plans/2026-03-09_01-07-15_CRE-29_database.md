# Implementation Plan

## 1) Database goals and invariants

Design persistence so lifecycle gating and lineage are first-class and resumable:

- Represent **wait states** explicitly (awaiting plan approval, awaiting PR review).
- Represent **iteration lineage** explicitly (plan v1/v2/v3, implementation attempt n, restart threads).
- Preserve compatibility with existing task list/query surfaces.
- Reuse existing Linear follow-up relationship behavior, but persist swarm-side linkage so workflow logic is reconstructable from DB alone.

Core invariants to enforce:

1. Every revision/attempt belongs to exactly one root task thread.
1. Every new revision knows its predecessor (or predecessor artifact) when it is not the first revision.
1. Gate waits are queryable without reconstructing from spans.
1. Status transitions are auditable (at minimum via timestamps + event rows; ideally dedicated history table).

## 2) Schema evolution strategy

### 2.1 Create new migration (do not edit 006 in-place)

Add `harness/internal/db/migrations/00X_swarm_lifecycle_lineage.sql` and register in `harness/internal/db/db.go` migrationFiles.

Keep 006 intact for historical correctness; perform additive changes + data backfill.

### 2.2 Extend task status enum/check

Current `swarm_tasks.status` only supports pending/running/completed/failed/canceled. Extend CHECK to include lifecycle gate states required by request:

- `awaiting_plan_review` (agent review stage gate, if persisted at task level)
- `awaiting_human_plan_approval`
- `plan_revision_requested`
- `implementing`
- `verifying`
- `awaiting_pr_review`
- `revision_needed`
- `restarting`

If minimizing status explosion is preferred, keep coarse statuses and move fine-grained state into a dedicated lifecycle table; however request explicitly calls for extending status/state modeling, so include at least human gate states in task status.

### 2.3 Add lifecycle state table (recommended)

Add `swarm_task_lifecycle` table to separate current phase/substate from terminal status:

- `task_id` (PK/FK)
- `phase` (classification/planning/implementation/pr/review/project)
- `substate` (awaiting_approval, in_progress, revision_requested, etc.)
- `gate_kind` (plan_approval, pr_review, none)
- `waiting_since`, `resumed_at`, `updated_at`
- `context_json` (review feedback, failure summary, routing rationale)

Rationale: avoids overloading `swarm_tasks.status`, enables richer gate semantics without constantly growing CHECK on primary tasks table.

### 2.4 Add revision/thread lineage table

Add `swarm_task_revisions`:

- `id` TEXT PK
- `task_id` FK swarm_tasks(id)
- `revision_number` INTEGER NOT NULL
- `parent_revision_id` nullable self-FK
- `root_task_id` FK swarm_tasks(id)
- `linear_issue_id` nullable (current revision ticket)
- `linear_parent_issue_id` nullable (for follow-up chain reference)
- `trigger` CHECK (`initial`, `plan_revision`, `review_revision`, `full_restart`)
- `created_at`
- Unique `(task_id, revision_number)`.

This lets one swarm task maintain internal revisions OR model each revision as separate task linked by root_task_id. Choose one model and enforce it consistently:

- Preferred for minimal API churn: **single task with revision rows**.
- If workflow chooses new task per full restart, store `root_task_id` + `parent_task_id` in tasks.

### 2.5 Add attempt/version linkage across artifacts/tickets

Extend `swarm_artifacts` with lineage metadata:

- `revision_id` FK swarm_task_revisions(id)
- `attempt_number` INTEGER default 1
- `version_label` TEXT (e.g., plan-v2, impl-attempt-3)
- `parent_artifact_id` nullable FK swarm_artifacts(id)
- broaden `artifact_type` CHECK to include:
  - `plan_review_doc`
  - `implementation_patch`
  - `verification_report`
  - `pr_summary`
  - `project_plan_doc`
  - `dependency_graph_doc`
  - `classification_report`

Alternative is new `swarm_artifact_versions` table; for SQLite simplicity and existing query patterns, additive columns on swarm_artifacts are acceptable.

### 2.6 Add review/gate decisions table

Add `swarm_gate_decisions`:

- `id` PK
- `task_id` FK
- `revision_id` FK nullable
- `gate_type` CHECK (`plan_approval`,`pr_review`)
- `decision` CHECK (`approved`,`revision_needed`,`full_restart`,`merged`)
- `decider_user_id` nullable FK users(id)
- `feedback_text`
- `created_at`

Needed to support resumable revisions and auditable human gate outcomes.

### 2.7 Add PR linkage persistence

Either add to `swarm_task_revisions` or separate `swarm_prs` table:

- `github_repo`
- `pr_number`
- `pr_url`
- `head_sha`
- `status` (`open`,`merged`,`closed`)
- `linked_linear_issue_id`

Given multiple revision attempts can create multiple PRs, a separate `swarm_prs` table keyed by revision is cleaner.

## 3) SQL query layer (sqlc) changes

Update `harness/internal/db/queries/swarm.sql` with explicit CRUD/query ops for new entities:

- lifecycle upsert/get (`UpsertSwarmTaskLifecycle`, `GetSwarmTaskLifecycle`)
- create/list revisions (`CreateSwarmTaskRevision`, `GetLatestSwarmTaskRevision`, `ListSwarmTaskRevisions`)
- artifact creation with lineage fields and targeted fetch (`GetArtifactsByRevision`, `GetLatestArtifactByTypeRevision`)
- gate decision writes/list (`CreateSwarmGateDecision`, `ListSwarmGateDecisionsByTask`)
- PR persistence (`CreateSwarmPR`, `GetSwarmPRByRevision`, `ListSwarmPRsByTask`)
- transition helpers (`UpdateSwarmTaskStatusAndLifecycle`) to reduce split-brain updates.

Then regenerate sqlc and update enum constants in `harness/internal/db/sqlc/enums.go` for any new CHECK values.

## 4) Migration/backfill details

Backfill rules in migration SQL:

- Existing tasks map to lifecycle phase/substate heuristically:
  - pending → phase=classification, substate=pending
  - running → phase=planning (or existing primitive-specific default), substate=in_progress
  - completed/failed/canceled → terminal substates
- Seed initial revision row (`revision_number=1`, trigger=`initial`) for every existing swarm task.
- Existing artifacts get `revision_id`=seed revision, `attempt_number`=1, `version_label` derived from type.

Add indexes:

- `idx_swarm_revisions_task_revnum`
- `idx_swarm_artifacts_revision`
- `idx_swarm_gate_decisions_task_gate`
- `idx_swarm_lifecycle_phase_substate`

## 5) Integration contract for orchestration/API consumers (DB-facing)

Database domain should define transition contract consumed by workflow/API layers:

- Only valid gate-enter transitions can set `awaiting_human_plan_approval` and `awaiting_pr_review`.
- Resume actions must create a `swarm_gate_decisions` row before status/lifecycle changes.
- Plan revision requested must increment `revision_number` and write linked Linear follow-up issue ID on the new revision row.
- Full restart must either:
  - create new task with `parent_task_id` and same `root_task_id`, or
  - create new revision with trigger `full_restart`.

Document this in comments in query file + migration to prevent drift.

## 7) Risks and design decisions to resolve early

- **Single-task-with-revisions vs multi-task lineage model**: choose before migration to avoid rework.
- **Status granularity boundary**: keep task.status coarse and lifecycle detailed, or fully encode phases in status. Recommend hybrid (coarse terminal + key gates in status, detailed lifecycle in table).
- **Artifact type expansion** may require UI filters updates; keep old types valid.
- **Temporal resume semantics** may need durable signal payloads; DB must store enough feedback context independent of workflow memory.

## 8) Out of scope for database domain

- Implementing Temporal signal handlers and wait loops.
- Writing new JS agents under `agents/`.
- Implementing GitHub client APIs.
- UI/templ rendering details for new states and lineage trees.

Database domain delivers schema, queries, constraints, and persistence contracts that enable those domains.
