# Implementation Plan

## 1) Extend Temporal primitive model without breaking existing workflows

Use current orchestration patterns in `harness/internal/swarmorch/workflows.go` (`deferredCleanup`, `createStageSpan`, `completeStageSpan`, child workflows, fan-out) as the base abstraction layer instead of introducing new orchestration subsystems. Add new workflow entrypoints and child workflows that compose similarly to `ResearchWorkflow` and `CodeChangePlanWorkflow`.

Planned workflow set:

- `TaskRouterWorkflow` (classification + dispatch)
- `CodeChangeLifecycleWorkflow` (parent lifecycle orchestrator)
- `PlanRevisionLoopWorkflow` (iterative loop)
- `ImplementationVerificationLoopWorkflow`
- `PRCreationWorkflow` (could be stage-only first, child if complex)
- `HumanReviewGateWorkflow` (signal-driven wait states)
- `ProjectWorkflow` (decomposition + dependency execution)

Keep activity option split (`agentActivityOpts`, `infraActivityOpts`) unchanged, reuse span hierarchy and artifact persistence patterns.

## 2) Introduce resumable/gated lifecycle states and decisions

Current enum (`pending/running/completed/failed/canceled`) is insufficient for explicit human waits. Add states in migration/sqlc for at least:

- `awaiting_plan_review`
- `awaiting_pr_review`
- `revision_requested`
- `awaiting_resume` (optional generic gate)

Also add decision/event payload conventions (stored in task messages/events and optionally dedicated columns/tables) so workflows can resume deterministically from signals/updates rather than polling.

DB work items:

- Migration update in `harness/internal/db/migrations/006_swarm_tables.sql` (or additive migration)
- Query additions in `harness/internal/db/queries/swarm.sql` for gate transitions
- Regenerate sqlc types (`harness/internal/db/sqlc/enums.go`)

## 3) Implement task classification + routing as Temporal-first entry

Replace endpoint-selected primitive behavior in `harness/internal/server/swarm_api.go` and `harness/internal/server/swarm_dashboard.go` with a single creation path that starts `TaskRouterWorkflow`.

`TaskRouterWorkflow` stages:

1. `classification` stage span runs `RunTaskClassifier` activity (`agents/task-classifier.js`), returns `{kind: question|code_change|project, confidence, rationale}`.
1. Route to child workflow:
   - question → `ResearchWorkflow`
   - code_change → `CodeChangeLifecycleWorkflow`
   - project → `ProjectWorkflow`
1. Persist classifier artifact + emit narrative message with route rationale.

Maintain backward compatibility by keeping old endpoints but internally forwarding to the router.

## 4) Plan Revision Loop design

Create `PlanRevisionLoopWorkflow` used inside `CodeChangeLifecycleWorkflow`.

Loop algorithm:

- Attempt counter starts at 1.
- For each attempt:
  1. Run planning pipeline (existing `CodeChangePlanWorkflow` logic extracted into reusable child/stage function).
  1. Run `plan_review` stage via `RunPlanReviewer` activity (`agents/plan-reviewer.js`) producing structured completeness review + revision suggestions.
  1. Transition task to `awaiting_plan_review`, emit event, wait for human decision signal/update (`approve` or `revise`).
  1. If approved → return approved plan artifact metadata.
  1. If revision requested → call existing `CreateLinearFollowup` activity to create linked ticket; append feedback/context; increment attempt and continue.

For lineage:

- Encode attempt number in artifact metadata/path suffix (`..._v2.md`) and span names (`planning_v2`).
- Persist linkage between attempt artifacts (either via new artifact parent field or message metadata if schema defers).

## 5) Implementation↔Verification retry loop (Max’s Bolt)

Add `ImplementationVerificationLoopWorkflow` under code-change lifecycle.

Per iteration:

1. `implementation` stage: run `RunImplementationAgent` (`agents/implementation-agent.js`) using approved plan + latest failure context.
1. `verification` stage: parallel fan-out checks (reuse `workflow.Go`/channel pattern already present):
   - unit/integration (`go test`, rust checks as configured)
   - E2E Playwright
   - manual Playwright CLI checklist artifact
1. Aggregate results activity returns pass/fail + failure bundle.
1. If fail and attempts < max → narrative message + loop to implementation with failure bundle.
1. If pass → emit verified artifact and continue to PR stage.
1. If max exceeded → fail workflow with structured reason + keep artifacts.

Bound retries with configurable max (workflow input/config) and optional backoff timer to avoid thrash.

## 6) PR creation stage

Add PR stage after successful verification in lifecycle workflow.

Temporal side:

- `pr_creation` stage span
- Agent drafts summary/body (`agents/pr-drafter.js`) from plan + implementation diff + verification artifacts.
- Activity invokes GitHub client wrapper to create PR, returns URL/number.
- Persist PR artifact and link/comment to Linear via existing non-fatal linear helpers.

Infra requirement:

- New GitHub client module analogous to `internal/linear` (auth token, repo owner/name config in `main.go`/config).
- New activities in `harness/internal/swarmorch/activities.go` for create PR/update PR comment.

## 7) Human review gate waits + resume paths

After PR creation, enter `HumanReviewGateWorkflow` or a stage with signal handlers.

Decision outcomes:

- `merge` → mark task completed, update Linear Done, close spans.
- `revision_needed` → feed review feedback back into `PlanRevisionLoopWorkflow` (new revision ticket linked to current).
- `full_restart` → create new Linear ticket referencing prior attempt; start fresh lifecycle child workflow, maintain parent span lineage.

Temporal implementation detail:

- Prefer signal-based waiting (`workflow.GetSignalChannel`) with durable payload rather than external DB polling.
- Add API endpoints in `swarm_api.go` for posting gate decisions by task/workflow id.
- Add dashboard controls in `swarm_dashboard.go` to submit decisions.

## 8) Project workflow and dependency orchestration

Implement `ProjectWorkflow` for decomposition + orchestrated execution.

Stages:

1. `project_decomposition`: agent creates research questions + parent tickets map.
1. `project_summary`: compresses context artifact.
1. `dependency_planning`: agent outputs DAG + Graphite stack order + Linear dependency edges.
1. `execution_orchestration`:
   - Start independent branches in parallel child workflows.
   - Sequence dependent branches using child workflow completion futures.
   - Each node routes to research/code-change subworkflow via same router logic.

Persist dependency graph artifact and reflect dependencies in Linear via wrapper calls.

## 9) Manager/registration/API wiring

In `harness/internal/swarmorch/manager.go`:

- Register new workflows/activities with worker.
- Ensure task queue reuse (`swarm-agents`) unless separation needed.

In `harness/internal/server/server.go`:

- Add/replace routes for unified task creation and gate decision submission.

In `harness/internal/server/swarm_api.go`:

- New endpoints: `POST /api/swarm/tasks` (unified), `POST /api/swarm/tasks/:id/plan-gate`, `POST /api/swarm/tasks/:id/review-gate`.
- Keep cancel semantics unchanged.

## 10) Rollout and migration strategy

1. Land schema/status updates first (compatible read paths).
1. Land workflow/activity registrations behind feature flag (e.g., `CM_SWARM_NEW_PRIMITIVES=true`).
1. Enable router endpoint while preserving old endpoint aliases.
1. Enable human-gate UI controls.
1. Enable project orchestration last (highest complexity/history growth risk).

## Out of scope (temporal domain)

- Full UX polish of dashboard tabs/messages (only minimal controls needed for gate decisions).
- Deep GitHub client implementation details beyond activity contract and workflow integration points.
- Non-Temporal agent prompt quality tuning.
- Graphite CLI/runtime execution specifics beyond artifact generation/orchestration metadata.
