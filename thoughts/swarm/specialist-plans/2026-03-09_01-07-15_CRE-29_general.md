# Implementation Plan

## 1) Extend lifecycle model for human gates + iterative attempts

1. Add explicit swarm lifecycle states to support waiting/resume semantics currently missing from `pending|running|completed|failed|canceled`.
   - Introduce statuses like `awaiting_plan_approval`, `awaiting_pr_review`, `revision_requested`, `restarted` (final naming to match DB enum conventions).
   - Update DB migration + sqlc enum generation so API/dashboard can persist and query these states.
1. Add attempt/revision metadata so v1/v2/v3 chains are explicit in swarm, not only implied by timestamps.
   - Add fields or companion table to track `parent_task_id`, `attempt_number`, `restart_of_task_id`, `linear_issue_id` snapshots.
   - Preserve existing span hierarchy; use span lineage for per-attempt trace and task lineage for cross-attempt trace.
1. Keep backward compatibility by mapping legacy tasks to unchanged states and only using new states for newly started lifecycles.

## 2) Add unified task classification + routing

1. Create `task-classifier.js` agent script using existing JSONL contract (start/event/question/heartbeat/outputPath).
1. Add new classifier input/output structs in `internal/swarmorch/types.go`.
   - Input: raw user request + optional hints (world/project context).
   - Output: `classification` enum: `question | code_change | project`, confidence, rationale.
1. Add activity in `activities.go` to run classifier agent and parse output artifact.
1. Refactor API/dashboard creation paths (`swarm_api.go`, `swarm_dashboard.go`) to:
   - accept a generic “new task” submission,
   - run classification before `CreateSwarmTask`,
   - dispatch starter workflow by classifier result (replacing manual endpoint/type split).
1. Keep existing explicit endpoints as compatibility wrappers that bypass classifier only when explicitly requested.

## 3) Implement Plan Revision Loop primitive

1. Add workflow: `PlanRevisionWorkflow` (or extend `CodeChangePlanWorkflow` with iterative mode).
1. Stages per attempt:
   - generate/obtain plan artifact,
   - run `plan-reviewer.js` completeness review,
   - set task status to `awaiting_plan_approval` and block on human signal.
1. Human gate API actions:
   - `approve` → continue to implementation loop,
   - `request_revision` → create Linear follow-up ticket via existing `CreateLinearFollowup`, spawn new attempt (v+1) linked to parent,
   - include reviewer feedback artifact/context in next attempt input.
1. Temporal mechanics:
   - use workflow signals for approval/revision decisions,
   - use child workflow per attempt for clean retry history and parent-level lineage,
   - maintain deterministic IDs via `workflow.SideEffect` patterns already used.

## 4) Implement Implementation & Verification Loop (Max’s Bolt)

1. Add `implementation-agent.js` to execute planned code changes (Claude Code-driven instructions + repo conventions).
1. Add `verification-agent.js` to run and summarize verification suites.
1. In workflow, model iterative loop:
   - implementation stage,
   - verification stage (parallelizable checks via `workflow.Go`/channel fan-out where useful),
   - on failure, append failure context artifact + loop back to implementation,
   - cap retries or expose operator cancel path.
1. Verification contract should include:
   - automated checks (`just check`, targeted go tests, any workflow-specific commands),
   - integration/e2e results,
   - manual Playwright CLI checklist outcome fields.
1. Persist structured verification summary artifact for PR and human review stages.

## 5) Add GitHub PR integration

1. Create GitHub client wrapper analogous to `internal/linear/cli.go`:
   - config/env (`GITHUB_TOKEN`, `GITHUB_OWNER`, `GITHUB_REPO` or equivalent),
   - methods for create PR, update PR body/title, add labels, comment.
1. Inject client into swarm manager/server similarly to Linear client wiring.
1. Add activities:
   - `CreatePullRequestActivity`,
   - optional `CommentOnPullRequestActivity` for updates.
1. Add `pr-summarizer.js` agent to produce PR title/body from:
   - approved plan,
   - implementation summary,
   - verification summary,
   - Linear linkage.
1. Workflow stage after verification pass:
   - create branch/commit assumptions documented (if handled outside swarm, call out integration contract),
   - call GitHub activity to open PR,
   - persist PR URL/number as swarm artifact + Linear comment/attachment.

## 6) Implement Human Review Gate (post-PR)

1. Add status `awaiting_pr_review` and corresponding dashboard/API controls.
1. Gate outcomes:
   - **Merge**: mark task completed, add final Linear update.
   - **Revision Needed**: route back to Plan Revision Loop with review feedback; create linked Linear follow-up.
   - **Full Restart**: create new top-level Linear ticket referencing previous attempt; start fresh workflow lineage while preserving backlink.
1. Ensure gate actions are idempotent (single transition accepted once) to avoid double-processing from repeated clicks.

## 7) Implement Project Workflow primitive

1. Add new workflow `ProjectWorkflow` that composes existing research + planning primitives.
1. Agent scripts:
   - `project-orchestrator.js`: decompose initiative into research questions + parent tickets,
   - `project-dependency-planner.js`: build Project Plan & Dependency Graph (parallel/sequential/independent).
1. Outputs/artifacts:
   - compressed summary,
   - dependency graph (machine-readable + markdown),
   - execution recommendation including Graphite stack plan and Linear dependency mapping.
1. Linear integration:
   - create/relate parent + child issues,
   - encode dependency links using existing relation operations in wrapper.

## 8) Operational/documentation updates

1. Update `harness/CLAUDE.md` and skill docs with:
   - new primitives,
   - task lifecycle states,
   - human gate operations,
   - GitHub env requirements,
   - endpoint usage changes (classification-first).
1. Add runbook notes for failure modes:
   - Temporal workflow stuck at gate,
   - GitHub API failures,
   - Linear follow-up creation rollback behavior.
1. Add observability expectations:
   - span names per new stage,
   - required artifact types at each stage for auditability.

## 9) Suggested delivery sequencing

1. **Phase A (foundation):** DB status/lineage + API/status read/write compatibility.
1. **Phase B (routing):** classifier script/activity + unified task creation path.
1. **Phase C (plan loop):** plan review agent + approval/revision signals + Linear follow-up chain.
1. **Phase D (implementation loop):** implementation/verification agents + retry loop.
1. **Phase E (PR):** GitHub client/config + PR summarizer + PR creation stage.
1. **Phase F (human review + restart):** post-PR gate and transitions.
1. **Phase G (project primitive):** decomposition/dependency workflow + Graphite/Linear planning artifacts.
1. **Phase H (docs/ops hardening):** runbooks, dashboards polish, and validation.

## Out of scope (general planner explicitly not implementing here)

- Detailed DB migration SQL text and sqlc query definitions (owned by database specialist).
- Frontend UI implementation specifics beyond required gate controls and status visibility (owned by UI specialist).
- Exact Git branch/commit automation internals if delegated to external tooling/Claude Code runtime.
- Organization-specific Graphite API integration details (only planning output contract is in scope here).
