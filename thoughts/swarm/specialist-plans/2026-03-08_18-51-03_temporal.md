# Implementation Plan

## Objective

Add Temporal worker status to `GET /health` as additive JSON while preserving existing liveness behavior (`200` + top-level `{"status":"ok"}`), and define a truthful status model that distinguishes:

1. disabled by config,
1. init failed,
1. initialized, while explicitly separating **current inference quality** from **future true runtime health**.

## Current code realities (verified)

- Health endpoint is currently fixed and minimal in `harness/internal/server/server.go` (`RegisterRoutes` at line ~141, `handleHealth` at ~302-304): always returns `map[string]string{"status":"ok"}` with HTTP 200.
- Swarm manager is optional and injected via `Server.SwarmManager *swarmorch.SwarmManager` (`harness/internal/server/server.go`, struct field at ~60).
- Swarm manager init is optional in `harness/main.go:initSwarmManager` (~498+):
  - returns `nil` when `CM_SWARM_TEMPORAL != "true"`.
  - returns `nil` on repo-root/config/Temporal init failure (logs error).
  - returns manager pointer on success.
- `SwarmManager` lifecycle in `harness/internal/swarmorch/manager.go`:
  - `NewSwarmManager` dials client, creates worker, registers workflows/activities, starts worker.
  - On `w.Start()` failure it returns error.
  - `Stop()` only stops worker and closes client; no persisted lifecycle state.
  - No status accessor exists today.

## Phase 1: Additive health payload with high-confidence startup/config inference

### 1) Expand `handleHealth` response shape (no breaking changes)

In `harness/internal/server/server.go`, replace the string-only payload with a structured map/struct that preserves:

- `status: "ok"` (unchanged top-level value)
- HTTP 200 always for process liveness

Additive fields proposal:

- `temporal.enabled` (bool): inferred from config intent (see wiring below)
- `temporal.worker_state` (enum string): one of
  - `"disabled"`
  - `"init_failed"`
  - `"initialized"`
- `temporal.health_confidence` (enum): initially `"startup_only"`
- `temporal.notes` (optional string): clarifies this is not runtime liveness of worker loop

### 2) Remove nil ambiguity by passing init intent/result into `Server`

`SwarmManager == nil` is ambiguous (disabled vs failed). Add explicit server fields in `harness/internal/server/server.go` `Server` struct:

- `SwarmTemporalEnabled bool` (from env intent)
- `SwarmTemporalInitError string` (empty when none)

Populate in `harness/main.go` near current swarm setup:

- compute `swarmEnabled := os.Getenv("CM_SWARM_TEMPORAL") == "true"`
- adjust `initSwarmManager` flow to also return an error/string outcome OR capture failure reason in main
- set `srv.SwarmTemporalEnabled` and `srv.SwarmTemporalInitError`

This allows deterministic classification:

- `enabled=false` => `disabled`
- `enabled=true && manager=nil && initError!=""` => `init_failed`
- `enabled=true && manager!=nil` => `initialized`

## Phase 2: Temporal manager status accessor for explicit lifecycle state

Even for startup-only signal quality, avoid recomputing from scattered fields by adding a status accessor in `harness/internal/swarmorch/manager.go`.

### 3) Introduce lightweight status model in manager

Add:

- type `WorkerState string` constants: `disabled|init_failed|initialized|stopping|stopped` (the latter two optional but useful once `Stop()` called)
- type `ManagerStatus struct` with minimal fields:
  - `WorkerState WorkerState`
  - `StartedAt *time.Time`
  - `StoppedAt *time.Time`
  - `LastError string`
  - `HealthConfidence string` (`startup_only` for now)

In `SwarmManager` struct add guarded fields (`sync.RWMutex` or atomics) for started/stopped timestamps and last error.

### 4) Track lifecycle transitions

- In `NewSwarmManager`: set started timestamp after `w.Start()` success.
- In `Stop()`: set stopping/stopped timestamps before/after stop/close.
- Add `Status() ManagerStatus` accessor to return snapshot.

Note: init-failed still happens before manager instance exists, so this status is complementary to main-level init outcome.

## Phase 3: Define “true runtime health” instrumentation (follow-on needed)

Current initialized state does **not** prove ongoing worker health. For true runtime health, plan incremental instrumentation:

1. **Dependency probes** in manager (or separate health service):
   - Temporal client connectivity check (lightweight API call with timeout)
   - Worker poll/execution vitality signal (last successful activity/workflow dispatch timestamp)
1. **Error latch + freshness windows**:
   - `lastWorkerError`, `lastSuccessfulPollAt`, `lastWorkflowStartAt`
   - derived runtime health: `ok|degraded|error`
1. **Status confidence upgrade path**:
   - from `startup_only` -> `runtime_probed`
1. **Accessor contract**:
   - `RuntimeHealth()` or expanded `Status()` including derived `Healthy bool`, `Reason`, `CheckedAt`

Until these exist, `/health.temporal.worker_state=initialized` must be documented as “initialized successfully at startup,” not “currently healthy.”

## Phase 4: Endpoint contract and compatibility safeguards

- Keep route and method unchanged: `GET /health`.
- Keep HTTP status 200 for harness process liveness regardless of temporal state.
- Keep top-level `status: "ok"` for existing consumers (scripts/monitor currently rely mainly on HTTP success; some may inspect this field).
- Add only nested/extra fields so old callers remain unaffected.

## Testing and verification plan

1. **Unit tests for classification logic** (`harness/internal/server/server_health_test.go`):

   - disabled: enabled false, manager nil => temporal.worker_state=disabled
   - init failed: enabled true, manager nil, initError set => init_failed
   - initialized: enabled true, manager non-nil => initialized
   - assert top-level `status=="ok"` and HTTP 200 in all cases

1. **Manager lifecycle tests** (`harness/internal/swarmorch/manager_test.go`):

   - status snapshot after construction includes startup-only confidence
   - `Stop()` transitions populate stopped fields (with mocked worker/client wrappers if needed)

1. **Manual smoke checks**:

   - run harness with `CM_SWARM_TEMPORAL=false`, call `/health`
   - run with `CM_SWARM_TEMPORAL=true` and Temporal unavailable to force init-failed signal
   - run with Temporal available for initialized signal

## Risks / caveats to explicitly document in code comments

- Nil manager cannot indicate failure vs disabled unless init intent/error are wired from `main.go`.
- Runtime worker death after successful startup will be invisible without active probes.
- Overly strong field names like `healthy=true` should be avoided until true runtime checks exist; prefer `worker_state` + `health_confidence`.

## Cross-domain handoffs

- API/Server domain: finalize response schema naming and backward-compatible JSON formatting.
- Monitoring/UI domain: optionally consume new temporal fields for display without changing alerting semantics tied to HTTP code.
- Docs/Ops domain: update runbooks to clarify `/health` remains liveness; temporal subsection is component status with confidence level.
