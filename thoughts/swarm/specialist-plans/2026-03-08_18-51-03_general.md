# Implementation Plan

Keep `/health` as a liveness endpoint (HTTP availability) and extend response JSON additively with Temporal/Swarm component status metadata. In `harness/internal/server/server.go` (`RegisterRoutes` and `handleHealth` around current `/health` registration and handler), preserve status code `200` and existing `{"status":"ok"}` field for compatibility, then add optional nested fields (for example `components.swarm` / `components.temporal`) only when `s.SwarmManager != nil`.

Because `SwarmManager` currently only proves startup success in `harness/internal/swarmorch/manager.go` (`NewSwarmManager` starts worker; `Stop` stops worker) and does not expose continuous runtime state, add explicit low-confidence semantics first: e.g., `configured`, `startupSucceeded`, `runtimeHealthConfidence: "low"`, and a note-like field indicating runtime worker/process health is not continuously observed. If stronger fidelity is desired, plan a follow-up in temporal domain to add lifecycle/status tracking inside `SwarmManager` (timestamps, last successful workflow start, worker running flag transitions, optional lightweight Temporal probe with timeout).

Document semantics clearly: `/health` remains liveness (service reachable), while component status is informational and not readiness gating. Update `harness/E2E_PLAYBOOK.md` health section (currently expects only `{"status":"ok"}`) to describe additive fields and that consumers should continue relying on HTTP success. Add/adjust tests in `harness/internal/server/server_test.go` to lock backward compatibility (always 200, includes `status: ok`) and assert additive swarm fields do not remove/rename existing keys. If introducing new SwarmManager status accessors in `manager.go`, cover them in `harness/internal/swarmorch/manager_test.go`.

Cross-cutting rollout: audit monitor/scripts consumers (request notes scripts rely mostly on HTTP code) and explicitly avoid introducing alerting behavior based on new JSON until confidence improves. Communicate constraints/limitations in release notes: Temporal worker status is best-effort, not authoritative runtime guarantee unless extra probes are implemented. If any scripts parse body strictly, coordinate additive-schema tolerance before deployment.
