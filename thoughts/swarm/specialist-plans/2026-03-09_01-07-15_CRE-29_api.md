# Implementation Plan

## 1) Route architecture changes: replace manual primitive entrypoints with classifier-driven start

### Current baseline to preserve

- Swarm API is hook-secret protected (`/api/swarm` group in `harness/internal/server/server.go`).
- Swarm dashboard endpoints are approved-session protected (`approved.GET/POST("/swarm/*")` in `server.go`).
- Current API split is manual by endpoint:
  - `POST /api/swarm/tasks/research` → `handleSwarmStartResearch`
  - `POST /api/swarm/tasks/code-change-plan` → `handleSwarmStartCodePlan`
- Current dashboard split is manual by `new_task_type` signal in `handleSwarmStartTaskDashboard` (`harness/internal/server/swarm_dashboard.go`).

### Planned API surface

1. Add a unified start endpoint:
   - `POST /api/swarm/tasks` (new)
   - Body: `{ requestText, ticketID? }`
   - Internally classifies into `question | code_change | project` and maps to primitive/workflow.
1. Keep existing `POST /api/swarm/tasks/research` and `/tasks/code-change-plan` temporarily as compatibility shims:
   - Either hard-route via existing behavior or call unified starter with forced override.
   - Mark as deprecated in handler comments and API response metadata.
1. Dashboard `/swarm/start` will ignore/remove manual `new_task_type` and call same shared classifier routing helper used by API.

### Code-level plan

- In `harness/internal/server/swarm_api.go`:
  - Refactor `startSwarmTask(...)` into a more generic helper that can accept resolved routing output (primitive + starter + classification metadata).
  - Add `handleSwarmStartTask` (new unified handler).
  - Introduce a small resolver function in server layer, e.g. `resolveTaskRoute(ctx, requestText) (primitiveType, workflowStarter, classification, error)` that delegates classifier logic to manager/orchestrator layer.
- In `harness/internal/server/server.go`:
  - Register new route `swarmAPI.POST("/tasks", s.handleSwarmStartTask)`.
  - Leave existing start routes for backward compatibility in first pass.
- In `harness/internal/server/swarm_dashboard.go`:
  - Remove branching on `signals.NewTaskType` from `handleSwarmStartTaskDashboard`.
  - Reuse same route resolver path as API so behavior is identical for webhook and human dashboard entry.

## 2) Human gate API endpoints: approve / request revision / restart / resume

### New endpoint set (hook-auth + dashboard-session equivalents)

For machine-to-machine control:

- `POST /api/swarm/tasks/:taskID/approve`
- `POST /api/swarm/tasks/:taskID/request-revision`
- `POST /api/swarm/tasks/:taskID/restart`
- `POST /api/swarm/tasks/:taskID/resume`

For dashboard actions (Datastar signal handlers):

- `POST /swarm/approve`
- `POST /swarm/request-revision`
- `POST /swarm/restart`
- `POST /swarm/resume`

### Handler behavior contract

Each action handler should:

1. Load task by ID (`s.DB.GetSwarmTask`) with consistent 404/500 semantics already used by cancel/get handlers.
1. Validate workflow ID exists when signaling existing workflow.
1. Validate action is allowed from current task status (new waiting states; see section 3).
1. Dispatch to new manager methods (API domain depends on swarmorch):
   - `SwarmManager.SignalApprove(...)`
   - `SwarmManager.SignalRequestRevision(...)`
   - `SwarmManager.SignalRestart(...)`
   - `SwarmManager.ResumeTask(...)` (signal or start new run depending on primitive semantics)
1. Persist immediate status transition where appropriate (or rely on workflow activity update if centralized there), but keep pattern consistent with existing cancel behavior.
1. Publish `EventBus.Publish("swarm", ...)` so SSE updates other clients quickly.

### Request payloads

- `request-revision`: requires feedback text (`reason`/`feedback`) and optional reviewer identity.
- `restart`: optional reason; if full restart implies new Linear ticket, workflow layer will perform follow-up creation.
- `resume`: optional context override.

## 3) Task state and middleware consistency

### API consistency requirements

- Do **not** alter existing auth layering conventions:
  - Hook secret for `/api/swarm/*` (`hookSecretMiddleware()` inline group usage).
  - Session + approved middleware for `/swarm/*` dashboard actions.
- Reuse existing error style (`echo.NewHTTPError`) and response structure (`{status: ...}`, IDs, etc.).

### Needed state model expansion (API-facing impact)

Current statuses in code path are only pending/running/completed/failed/canceled (from generated enums). For gates/resume we need explicit API-visible waiting states such as:

- `awaiting_plan_approval`
- `revision_requested`
- `awaiting_pr_review`
- `awaiting_resume` (if used)

API plan dependencies on DB/orchestration:

- Add status values in schema + sqlc enum generation.
- Update API/dashboard “active task” logic in `firstActiveTaskID(...)` and SSE heartbeat checks in `swarm_dashboard.go` so waiting states are treated as active/relevant (not dropped from detail pane refresh).

## 4) SSE and dashboard event behavior alignment

### Existing SSE behavior to preserve

- `/swarm/events` subscribes to `EventBus` topic `swarm` and patches sidebar/detail via Datastar (`patchSwarmSidebar`, `patchSwarmDetail`).
- Heartbeat refresh every 30s for pending/running tasks.

### Planned adjustments

1. Extend active-status checks to include human-gated waiting statuses.
1. Ensure gate action handlers publish swarm events after signal/start.
1. Ensure detail patch includes latest messages/artifacts/spans after gate actions; no custom SSE channel needed.
1. Keep selector IDs and patch functions unchanged to avoid frontend regressions (`swarm-sidebar`, `swarm-detail`).

## 5) Primitive coverage mapping (API orchestration entrypoints)

Add API routing/start hooks for newly required primitives in coordination with `internal/swarmorch`:

- Plan Revision Loop primitive starter (or phase within code-change lifecycle).
- Implementation & Verification Loop starter/signal integration.
- PR Creation phase trigger (likely internal phase after verification pass; API mainly exposes status/gates).
- Human Review Gate actions (explicit API endpoints above).
- Project Workflow starter for classifier “project” results.

API-side design decision: prefer **single lifecycle workflow entrypoint** for code-change tasks and drive phase transitions via signals, rather than separate public endpoints per phase. This keeps external contract simple and aligns with requested classifier-driven routing.
