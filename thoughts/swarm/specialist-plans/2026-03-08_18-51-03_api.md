# Implementation Plan

## 1) Confirm existing health contract and preserve compatibility

- In `harness/internal/server/server.go` (`RegisterRoutes` and `handleHealth`), preserve:
  - `GET /health` route path
  - HTTP `200` response for current baseline operation
  - top-level JSON `{"status":"ok"}` compatibility contract
- Do **not** repurpose top-level `status` to reflect worker failure states initially. Keep this stable for existing callers that rely on success and minimal parsing.

## 2) Define additive response shape for temporal/swarm health

Introduce additive fields in `handleHealth` response while retaining existing top-level fields. Proposed shape:

```json
{
  "status": "ok",
  "swarm": {
    "status": "ok|degraded|unknown",
    "worker": {
      "configured": true,
      "started": true,
      "running": true,
      "last_error": "...",
      "last_heartbeat": "RFC3339 timestamp"
    },
    "temporal": {
      "namespace": "swarm",
      "reachable": true
    }
  }
}
```

Guidelines:

- `status` remains the legacy compatibility indicator.
- New nested `swarm.status` is the richer health rollup for new consumers.
- Use `unknown` when the manager cannot assert live state (better than false precision).

## 3) Add/extend swarm manager runtime state surface

- Inspect and update `harness/internal/swarmorch` manager files (expected around `swarm_manager.go`) to expose a read-only snapshot API, e.g.:
  - `func (m *SwarmManager) HealthSnapshot() HealthSnapshot`
- Ensure snapshot includes lifecycle-derived fields (configured/started/running/last error/time), not just startup success.
- If current architecture has only init-time signals, implement minimal lifecycle tracking hooks where worker start/stop/error paths already occur.
- Keep this non-blocking and lock-safe for HTTP handler reads.

## 4) Update `handleHealth` implementation in harness server

- In `harness/internal/server/server.go:302+` (current `handleHealth`), move from static map to struct/map response assembly:
  - always set top-level `status: "ok"`
  - when `s.SwarmManager != nil`, add `swarm` object from `HealthSnapshot()`
  - when `s.SwarmManager == nil`, either omit `swarm` or return `swarm.status: "unknown"` with `configured:false`
- Keep HTTP status code `200` for now, even if swarm reports degraded.

## 5) Clarify naming and stability policy

- Prefer concise, operationally clear names:
  - top-level: `status`
  - subsystem: `swarm.status`
  - internals: `worker.running`, `worker.started`, `worker.last_error`
- Avoid adding fields with uncertain semantics unless marked optional/unknown.
- Document that additive keys may grow; existing keys remain backward-compatible.

## 6) Validate monitor compatibility and optional enhancement

- `site/internal/monitor/handler.go` currently checks harness `/health` primarily by HTTP success and does not require rich parsing.
- Verify no regressions with additive fields.
- Optionally add a follow-up enhancement to parse `swarm.status` for richer UI, but keep this out of required compatibility scope.

## 7) Tests and verification

- Add/adjust handler tests in `harness/internal/server/server_health_test.go`:
  - legacy assertion: `/health` returns 200 and includes `status: ok`
  - additive assertion: when swarm manager exists, response includes `swarm` object
  - degraded snapshot still returns HTTP 200 and preserves top-level status compatibility
- Add swarm manager tests in `harness/internal/swarmorch/...` verifying health snapshot transitions for start/error/stop states.
- Manual checks:
  - `curl -i /health` confirms HTTP 200
  - `jq` confirms `status == "ok"` and optional nested `swarm` payload

## 8) Rollout strategy

- Phase 1: additive payload only, no semantic change to HTTP status or top-level `status`.
- Phase 2 (optional, coordinated): introduce stricter readiness endpoint (e.g., `/ready`) for non-2xx behavior if ops needs hard-fail probes.
- Communicate to consumers: `/health` remains backward compatible; new fields are informational unless explicitly adopted.
